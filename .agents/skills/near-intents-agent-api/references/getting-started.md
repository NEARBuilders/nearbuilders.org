# Getting started: from partner key to a working agent

This walks a new partner from zero to an agent that can move money. Every step is plain HTTP, so
it works the same from any language; SDK equivalents are in the language references.

## 0. What you need

| Thing | Where it comes from | Where it lives |
|---|---|---|
| API base URL | `https://api.agentsonintents.com` (mainnet) | config `NEAR_INTENTS_AGENT_API_URL` |
| Partner API key `naa_…` | Partner dashboard → **API keys** | backend secret store `NEAR_INTENTS_AGENT_API_KEY` |
| Owner wallet | The end user: NEAR account, EVM wallet or passkey | the user's device; never your server (unless you deliberately run the owner key, see [architecture.md](architecture.md)) |
| Grant token `ngt_…` | Generated by your backend, one per agent session | your database, encrypted |

The hosted API is **mainnet with real funds**. Use small amounts and a dedicated owner account
while building.

## 1. Get a partner API key

1. Open the [partner dashboard](https://partners.near-intents.org/) and sign in.
2. Go to **API keys** → create a key, name it after the environment (`prod-backend`,
   `staging`).
3. Copy the `naa_…` token **now**. It is shown once and only its prefix is stored. Keys do not
   expire; revoke and replace them from the same page.

The dashboard also shows **Overview** (operation counters), **Agents** (every agent your keys
created, with cooldowns), **Health** and **Settings**. A tenant can hold up to 10 unrevoked keys.
Revoking a key stops new requests at once; operations already past the dispatch commit still
finish and the revoke response lists them.

Use one key per backend environment. All keys of a tenant see the same agents; agents belong to
the tenant, not the key, except that `/recover` must use the key that admitted the operation.

## 2. Smoke test

```bash
export NEAR_INTENTS_AGENT_API_URL=https://api.agentsonintents.com
export NEAR_INTENTS_AGENT_API_KEY=naa_...

curl -s "$NEAR_INTENTS_AGENT_API_URL/v1/network"                                  # public health + owner types
curl -s "$NEAR_INTENTS_AGENT_API_URL/v1/whoami"  -H "X-API-Key: $NEAR_INTENTS_AGENT_API_KEY"   # {api_key_id, tenant_id}
curl -s "$NEAR_INTENTS_AGENT_API_URL/v1/quotas"  -H "X-API-Key: $NEAR_INTENTS_AGENT_API_KEY"   # limits and usage
curl -s "$NEAR_INTENTS_AGENT_API_URL/v1/tokens" | head -c 600                      # asset catalogue
```

Or run `scripts/check_api.sh` from this skill. A `401 invalid_api_key` means the key is wrong,
revoked, has stray whitespace, or was sent to a different deployment than the one that issued it.

Default partner limits (check `/v1/quotas` for yours): 100 new agents per rolling 24 h, 10 API
keys, a per-minute request rate per tenant and per key, 100 deposit addresses per agent per 24 h, 10
concurrent `wait_ms` long-polls per key, 50 live grants per agent.

## 3. Pick tokens

`GET /v1/tokens` returns `{ data: [{ asset_id, symbol, decimals, blockchain, price, … }] }`.
Everything (policy assets, limits, executions) uses `asset_id`, for example
`nep141:wrap.near` (wNEAR, 24 decimals) or the USDC id for the chain you want. Amounts are
atomic strings: `to_atomic("1.5", 24)`. `price` is USD per whole token, `null` when unknown.

## 4. Create the agent account (owner signs once)

```http
POST /v1/generate-intent
X-API-Key: naa_…
Content-Type: application/json

{
  "type": "agent_create",
  "name": "Trading assistant",
  "external_user_id": "user_123",
  "owner": { "type": "near", "account_id": "alice.near", "public_key": "ed25519:…" },
  "policy": {
    "frozen": false,
    "actions": ["swap"],
    "confidential": false,
    "owner_approval": false,
    "assets": ["nep141:wrap.near", "<usdc asset_id>"],
    "limits": { "per_transaction": { "nep141:wrap.near": "5000000000000000000000000" } },
    "max_actions_per_hour": 20,
    "destinations": { "mode": "only", "list": [] },
    "budget": { "daily_usd": "50", "weekly_usd": null, "monthly_usd": "500" },
    "timelock_ms": 0
  }
}
```

Response (201): `correlation_id` (`intent_…`), `agent_id`, `expires_at`, `signer`,
`intent: { standard, payload }`, `preview: { summary, policy, … }`.

1. Show `preview.summary` and the policy to the owner.
2. The owner's wallet signs `intent.payload` unchanged (method by `intent.standard`, see
   [signing.md](signing.md)).
3. Submit:

```http
POST /v1/submit-intent
{ "type": "agent_create", "correlation_id": "intent_…",
  "signed_data": { "standard": "nep366", "payload": { …unchanged… }, "signed_delegate": "…" } }
```

4. Poll `GET /v1/status?correlation_id=intent_…&wait_ms=30000` until `SUCCESS`. Creation is on
   chain (the API's sponsor pays gas); it usually takes a few seconds to a minute.
5. `GET /v1/agents/{agent_id}/policy` → `status: "APPLIED"` and `provider_policy_synced: true`.

`owner` shapes:

```json
{ "type": "near", "account_id": "alice.near", "public_key": "ed25519:…" }
{ "type": "evm", "address": "0xabc…(lowercase)", "chain_id": 1, "public_key": "0x<128 hex, uncompressed, no 04>" }
{ "type": "passkey", "credential_id": "<b64url>", "public_key": "<b64url DER SPKI P-256>", "rp_id": "example.com", "origin": "https://example.com" }
```

A NEAR owner key must be a **FullAccess** key on that account. EVM and passkey owners need no
NEAR account: the API derives one and deploys it on first use, sponsored.

## 5. Issue a grant for the agent

```text
token      = "ngt_" + base64url_nopad(32 random bytes)        # keep secret, backend only
credential = sha256_hex(token)                                 # hash of the token STRING
```

```http
POST /v1/generate-intent
{ "type": "grant_issue", "agent_id": "…", "label": "assistant-session-42",
  "credential": "<64 hex>", "expires_at": "2027-01-01T00:00:00Z" }
```

Owner signs, you submit, status `SUCCESS` returns `details.grant.grant_id`. Store
`{grant_id, agent_id, encrypted token, label, expires_at}`. See [grants.md](grants.md).

## 6. Fund the account

```http
POST /v1/agents/{agent_id}/deposit
X-API-Key: naa_…
Idempotency-Key: dep_7f3c…
{ "origin_asset": "<asset_id on the chain the user pays from>" }
```

Returns `PENDING_DEPOSIT` with `details.deposit_address`, `details.memo` (send it when present),
`details.min_amount`, `details.expires_at`, `details.refund_to` (the agent account). Show those
to the payer, then poll the `correlation_id` until `SUCCESS`. On NEAR you can also send NEP-141
tokens straight to `GET /v1/agents/{agent_id}/addresses/near`.

## 7. Act as the agent

```http
POST /v1/agents/{agent_id}/swap
X-API-Key: naa_…
X-Grant-Token: ngt_…
Idempotency-Key: swap_9a1e…
{ "origin_asset": "nep141:wrap.near", "destination_asset": "<usdc>", "amount": "1000000000000000000000000", "dry": true }
```

`dry: true` returns `{dry: true, type: "swap", quote}` and nothing else (no key, no grant needed).
Drop `dry` to execute: you get `202` with a `StatusResponse` (`op_…`). Poll it to a terminal
status. See [executions.md](executions.md) and [status-and-recovery.md](status-and-recovery.md).

## 8. Before going live

- Walk the checklist in [architecture.md](architecture.md#security-checklist).
- Handle every code in [errors.md](errors.md) you can hit, at least the refusal and retry ones.
- Persist `correlation_id` + `Idempotency-Key` + request body before sending.
- Read `GET /v1/network` on a schedule and surface degraded components to users.
